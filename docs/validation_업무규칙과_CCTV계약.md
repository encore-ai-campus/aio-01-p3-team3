# Validation 업무 규칙과 CCTV 출력 계약 기준

## 1. `validation.py`에서 확인할 업무 규칙

여기서 **업무 규칙**은 자료형이 맞는지만 보는 검사가 아니라, 결과를 다음 단계에서 실제로 사용할 수 있는지 판단하는 조건입니다.

예를 들어 `fall_suspected`가 `true` 또는 `false`인지는 자료형 검사입니다. CCTV 분석 성공 결과에 `fall_suspected` 값이 반드시 있어야 Emergency Agent가 판단할 수 있다는 조건은 업무 규칙입니다.

| 대상 | README에 적힌 기준 | 추가로 정할 내용 |
|---|---|---|
| Vital | 값이 있고 측정 가능한 범위인지 검사 | 심박·혈압·체온 등의 허용 범위 숫자 |
| 실내 환경 | 온도와 습도가 측정 가능한 범위인지 검사 | 온도·습도 허용 범위 숫자 |
| CCTV | JSON 형식 및 `person_visible`, `posture`, `fall_suspected`, `description` 필수 여부 검사 | 분석 성공 상태에서 네 항목을 모두 필수로 적용할지 |
| LLM | JSON 형식과 필수 키 검사 | Emergency·Summary별 필수 키 목록 |
| 최종 실패 | 누락 정보 없이 진행하거나 안전 종료, 보호자 알림 및 로그 기록 | 각 결과가 실패했을 때 진행할지 종료할지의 구체 정책 |

현재 자료만으로 구체적으로 코드화할 수 있는 기준은 CCTV 필수 항목입니다. Vital과 실내 환경의 “측정 가능한 범위”는 숫자가 문서에 없으므로 범위를 먼저 정해야 합니다. LLM의 필수 키도 각 출력 계약과 맞춰야 합니다.

각 책임은 다음과 같이 나뉩니다.

- `validation.py`: 최종 결과가 약속한 출력 계약에 맞는지 검사
- AutoHealing: 검증 실패나 호출 오류 때 재시도·복구 수행
- Join Guard: 복구가 끝난 결과를 바탕으로 진행 또는 안전 종료 결정

예를 들어 “Vital 결과가 없으면 안전 종료”는 README에 정의된 정책이며, 검증 자체보다 Join Guard가 판단할 내용입니다.

## 2. CCTV 계약의 두 가지 선택지

현재 `CctvAnalysis` 모델에서 아래 필드들은 선택값입니다.

- `person_visible`
- `posture`
- `fall_suspected`
- `description`

따라서 현재 스키마만 적용하면 이 항목들이 빠져도 모델 검증을 통과할 수 있습니다.

### 선택지 A: 현재 스키마 기준

- 네 항목이 누락되어도 스키마상 유효할 수 있습니다.
- `validation.py`는 현재 모델이 허용하는 결과를 유효하다고 판단합니다.
- 수정 범위는 작습니다.
- 분석 성공 결과에 핵심 정보가 없어도 다음 단계로 전달될 수 있습니다.
- README의 “필수 키” 설명을 현재 스키마에 맞게 바꿔야 합니다.

### 선택지 B: README 기준으로 강화

- `status="analyzed"`일 때 네 항목을 모두 요구합니다.
- 하나라도 빠지면 출력 계약 위반으로 처리합니다.
- 해당 검사가 Agent/AutoHealing의 재시도 경로에 연결되어야 재시도할 수 있습니다.
- 재시도를 모두 소진하면 CCTV를 실패 또는 사용 불가로 처리하고, Join Guard 정책에 따라 “영상 판단 불가”로 표시한 뒤 바이탈 중심으로 진행합니다.
- 모델 또는 검증 규칙과 재시도 연결을 보완해야 하므로 수정 범위가 더 큽니다.

두 선택지의 핵심 차이는 **“분석 성공이라고 표시된 결과에 필수 관찰 정보도 반드시 있어야 하는가?”**입니다.

## 권장 기준

README에 CCTV 필수 키가 이미 적혀 있고 해당 값이 후속 위험 판단에 사용되므로, README 기준으로 강화하는 편이 더 일관적입니다.

이 경우 계약은 다음처럼 이해할 수 있습니다.

- `status="analyzed"`: 네 필드가 모두 있어야 함
- `status="failed"` 또는 `status="unavailable"`: 분석 필드가 없을 수 있음

다만 `description`이 빈 문자열이어도 허용할지는 README에 정해져 있지 않습니다. 우선 키가 존재하고 자료형이 맞는 것을 요구하고, 빈 문자열을 금지할지는 별도 합의할 수 있습니다.
