## 2. 장애 유형별 감지 조건·지표·복구 전략

모든 장애 처리는 `backend/src/healing/`의 공통 복구 계층이 담당하고, 결과는 `run_logs`에 단계별로 남습니다.
장애 주입은 실제로 무언가를 끊지 않고 요청의 `fault` 필드로 **코드에서 예외를 던지는 방식**입니다 (`vital`, `iot`, `vision`, `llm`).

| ID | 장애 유형 | 감지 조건 | 확인 지표 (`run_logs`) | 복구 전략 | 최종 실패 시 |
|---|---|---|---|---|---|
| DR-VITAL-01 | 바이탈 센서·조회 (네트워크·DB) | 시간 초과(15초), 연결 실패, 최근 측정값 없음(45초 초과), 센서 범위 밖 | `step=vital`, `status=retry/fallback/fail`, `error` | 3회 시도 → **캐시(이전 정상 측정값)** → MCP Mock | 바이탈 없음 → Join Guard 안전 종료 + 보호자에게 "센서 확인" 알림 |
| DR-IOT-01 | 기기 제어 (외부 도구) | 제어 결과 실패, 시간 초과(10초) | `step=action:control_device`, `status=retry/fail` | 3회 시도 (제어는 캐시로 대신할 수 없음) | **FAIL** → 보호자에게 "직접 조치 필요" |
| DR-VISION-01 | CCTV 비전 분석 (LLM·외부 API) | 응답 없음(60초), CCTV 출력 계약 위반, 형식 오류 | `step=vision`, `status=retry/fail` | 2회 시도 | "영상 판단 불가"로 표시하고 **바이탈 기준으로만 판정**, 원본 캡처를 보호자에게 표시 |
| DR-LLM-01 | 조치안·안내문 LLM | JSON 파싱 실패, 필수 키 누락, 금지 표현 | `step=llm`/`summary`, `status=retry/fallback`, `recovery=template` | 교정 재요청 1회 → **고정 템플릿 문구** | — (판정은 코드라 위험도·조치는 그대로 진행) |
| — | 실내·기기 상태 조회 | 시간 초과, 연결 실패, 범위 밖(실내 -10~60℃) | `step=iot_env`/`iot_devices` | 3회 시도 | 해당 정보 없이 진행, 화면에 "확인할 수 없습니다" |
| — | DB 자체 장애 (SQLite) | 잠김(BUSY/LOCKED), 기타 오류 | 로그 저장 실패 시 메모리 events로 전달 | 잠김은 재시도, 같은 DB 장애 시 캐시 건너뜀 | 바이탈 DB 오류 → 안전 종료 |
| — | MCP 서버 연결 | 연결 실패 (`McpConnectionError`) | 단계별 `retry` | 재시도 대상으로 분류 (도구 자체 오류는 재시도하지 않음) | 각 단계의 최종 실패 처리 |

### 재시도 횟수와 시간 제한 (코드 기준)

| 경로 | 시도 횟수 (최초 포함) | 시간 제한 |
|---|---:|---|
| 최신 바이탈 조회 | 3 | 조회 1회당 15초 |
| 실내·기기 상태 조회 | 3 | 도구 호출 1회당 15초 |
| 제어·119·알림 Mock 실행 | 3 | 조치 호출 1회당 10초 |
| backend → CCTV 분석 요청 | 2 | 분석 요청 1회당 60초 |
| MCP 내부 비전 LLM | 3 | 비전 LLM 호출 1회당 15초 |
| 문장 LLM (조치안·안내) | 2 후 템플릿 | LLM 호출 1회당 10초 |

## 5. 수동 개입 조건과 알림

| 상황 | 시스템 동작 | 보호자에게 보이는 것 |
|---|---|---|
| 바이탈 최종 실패 (캐시·Mock도 실패) | 안전 종료, `notify_guardian` (Mock) | "센서 상태를 직접 확인해 주세요" |
| 승인한 기기 제어 3회 실패 | `ActionResult.status=failed` | "제어에 실패했습니다. 직접 조치가 필요합니다" |
| CCTV 분석 실패 | 바이탈 기준 판정 | "영상 판단 불가" + 원본 캡처 확인 요청 |
| 119 자동 연결 실패 | 결과를 실패로 기록 | 보호자 안내에 실패와 직접 조치 요청 |
| 승인 대기 중 응답 없음 | 자동 실행하지 않음 (`ENABLE_TIMEOUT_119 = False`) | 다시 알림 (119는 승인 없이 걸지 않음, `VITAL_SEVERE` 제외) |

- **보호자 알림:** `notify_guardian`, `call_119` MCP 도구는 실제 전송 없이 로그만 남기는 Mock입니다.
- **운영 담당자 알림:** 장애를 운영 담당자에게 따로 알리는 채널(메신저·메일 연동)은 **구현하지 않았습니다.** 장애 기록은 `run_logs`와 화면의 AutoHealing 로그(`GET /logs`)로만 확인합니다.

## 6. 실패 사례와 한계 (숨기지 않고 기록)

| 항목 | 내용 |
|---|---|
| 시험 범위 | 장애 시험은 MCP·LLM을 시험용 응답으로 바꾼 **로컬 시험**입니다. 실제 LLM 키·비전 인식 정확도·배포 환경에서의 장애 복구는 이 증빙으로 검증되지 않았습니다. |
| LLM 키가 없을 때 | CCTV 분석이 "영상 판단 불가"가 되어 `induction`(사람 없음 판단)·`fall`(쓰러짐 판단)이 다르게 판정됩니다. 시연 환경에는 LLM 키가 필요합니다. |
| 캐시 조건 | 캐시는 시뮬레이터의 실시간 값으로만 채워집니다. 시뮬레이터 없이 `vital` 장애를 넣으면 캐시 대신 Mock 값으로 복구됩니다. |
| 승인 대기 | 메모리 저장이라 백엔드 재시작 시 사라집니다. |
| CCTV 중복 재시도 | backend 2회 × 내부 비전 3회로, 공급자 호출이 최대 6회까지 늘 수 있습니다. |
| 배포 중 화면 문제 | 테마가 Streamlit 툴바를 숨기면서 접힌 사이드바를 다시 열 수 없던 문제가 있었고, CSS 수정(PR #52)으로 고쳤습니다. 배포 후 자동 상태 확인이 없어 사람이 화면으로 발견했습니다. |
| 운영 알림 | 운영 담당자 알림 채널이 없습니다 (5장). |
